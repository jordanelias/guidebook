The Naming Register

Sixty-six tables, none of which tells you its stage. Forty-one foreign keys that cross a stage boundary, all landing on seven columns. And one word that means two opposite things in the same schema.

Measured 2026-08-27 Against data/guidebook.db · user_version 64 Status proposal — nothing executed
Nothing here is executed. No table is renamed, no migration is written, no caller is swept. The §R8 precedent sets the bar: renaming four tables is already owner-gated, scoped at 312 tracked files, and forbidden to attempt piecemeal. This covers sixty-six. It exists so the rename can be ruled on once, as a grammar, instead of table by table forever.

A.1 — The five ids

STAGES = ["research", "evidence-collection", "judgment", "synthesis", "render"]

def stage_label(stage_id: str) -> str:      # tools/pipeline_completeness.py:42
    return stage_id.replace("-", " ")

Substrate is not in that list and must not be added to it. It is the layer all five stages point into.

A.2 — The proposed prefix, derived rather than invented

An abbreviation table (research → res_) would be a second home for the stage name — the exact defect rule 5 exists to stop. So the prefix must be computed from the id, the same way the display label is:

def stage_prefix(stage_id: str) -> str:     # one line, one home
    return stage_id[:3] + "_"

All five are distinct at three characters. Substrate takes no prefix, and the absence is the signal — no prefix means not a stage. That is also the cheap answer: it leaves items, populations, slugs and terms — the four most-referenced names in the repository — untouched.

PART C Nine naming faults, each measured

Numbered because Part E cites them by number — the sequence carries information.

  1. No name carries its stage. 0 of 66 tables are prefixed. Rule 5 is unusable without knowing a table's stage, and deriving that map is a stopper in CLAUDE.md. The name is where the derivation should already live.
  2. "Locator" means two opposite things in one schema. source_locators holds doi, url, pmid, pmcid, isbn, issn, standard_number — bibliographic identifiers. Meanwhile R3 defines a locator as a within-document pointer ("clause/section/page"), which is what source_value_extractions' sixteen loc_* columns hold. The table named _locators holds the sense it is not.
  3. jurisdictional_values holds no values. 109 rows; value_text and value_numeric are 0 non-null, by the REFERENCE-ONLY ruling of 2026-08-12. The name states the opposite of the ruling.
  4. bpc_metadata is not metadata. It is the best-practice synthesis — the stage's output. BPC is also an unexpanded acronym living in a table name, two columns and a junction.
  5. Two tables named *_specs do not reference specifications. case_study_specs.item_code → items.item_code and economics_entry_specs.item_code → items.item_code. Named for the judgment object, keyed on the render rollup.
  6. Three suffixes for one relation kind. _links ×9, _map ×3, and seven bare-noun junctions. All are the same thing: a primary key composed of references to two other things.
  7. Head noun is plural in 52 tables and singular in 14.
  8. The activity is named, not the row. citation_mining, gap_mining, supersession_check name a process; one row is a run of it. Compare url_verification_runs, which gets this right.
  9. Retired vocabulary is still in four table names and six columns. Already ruled — the §R8 rename, then the register entry.

PART D The proposed grammar

<stage-prefix>  <subject>  <kind-suffix> — head noun always plural

Prefix — stage_id[:3] + "_", derived. No prefix means substrate.

Kind suffix — a closed set, each decided by a test against the schema itself rather than by taste:

KindTestSuffixExample
registryPK is a code this table mints, and other tables key to itnoneitems, populations
junctionPK composed of ≥2 columns that each identify another thing — a foreign key, or an external vocabulary with no table_linksevi_slug_links
runa record of an act performed, carrying a timestamp and an outcome_runsevi_url_verification_runs
recordanything else — one row is a thing that happened or was decidedplural noun naming what one row isres_searches, jud_specifications

The junction test is written against key columns rather than payload, because the payload test fails on real tables. term_aliases has PK (term_id, alias, language) and looks composite — but alias is the payload, so the row is a record, not a junction, and it keeps its name.

PART F What this does not decide

F.1 — items may not be substrate any more

The derived stage map (2026-08-25) files items under substrate as a vocabulary. The owner ruling of 2026-08-26 makes it "the Part-4 render rollup … derived from specifications rather than keyed by them." Under the derivation test — whose own work does this record? — a table derived from judgment output is render, not substrate.

If that reading holds, the cross-stage map in Part B changes underneath everything above: all 10 foreign keys targeting items.item_code are re-classified, and three of them stop being cross-stage at all because both ends land in render. The remaining seven — including four from judgment — become forward pointers, of the kind B.2 finds are otherwise almost absent. This is the highest-consequence open question here, and it is the owner's.

F.2 — The entity model's arrow runs backwards from the ruled pipeline

governance/conceptual-model.md:90 — "ENT-02 → ENT-03 → ENT-01 … Sources feed into BPC entries. BPC synthesis produces specifications."

That is evidence → synthesis → judgment. The ruled pipeline is evidence → judgment → synthesis. The model predates the ruling, and one of them has to be corrected — a rename executed against the wrong one bakes the contradiction into sixty-six names.

F.3 — Three tables are in no stage and not really substrate either

decisions (166), data_migrations (352), pipeline_runs (1) record the project's own acts, not the book's content. They are filed under substrate for want of anywhere else. A meta_ prefix is arguable; so is leaving them alone.

F.4 — Key kind is out of scope and should not be

Renaming search_executions does not fix exec_id being a rowid. A rename migration is the cheapest moment this project will ever have to also make the judgment stage's key a stable code — specifications holds 0 rows. After the first determination, it is re-reasoning.

PART G What it would cost

Now is the cheapest it will ever be

13 of the 66 tables — all of judgment and all of synthesis — hold zero rows, and every render table but rooms holds zero. A rename there is DDL only.

The sweep is the cost, not the SQL. A rename is not done until the callers are swept, and a view is a caller, and so is a skill. Migration 064 exists because 063 swept eight Python readers and six skills and missed one view. Here the caller set is:

CallerWhy it bites
18 views, 7 of them cross-stageeach one is a pointer that rule 5 protects from deletion
every db.py subcommand, dbcore, the Pydantic modelsschema ↔ model drift is a bug, not a convention
governance/check-registry.yamlencodes stage-qualified basis: references — it broke the selftest on the last stage rename
the skillsthey teach table names in prose, and nothing greps prose for correctness
scripts/migrations/data_*a column a committed data migration INSERTs can never simply be dropped — and the same replay-order trap that cost migration 062 applies to a table rename

One migration, or not at all. The bar on piecemeal execution applies with far more force at sixty-six tables than at four.
