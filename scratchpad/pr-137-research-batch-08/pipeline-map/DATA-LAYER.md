## 6. The item-layer trap, applied

Per CLAUDE.md §7, every `item_code`-keyed table was checked against the "0 rows and a rebuild does
not restore it" warning rather than assumed dead. `items` itself: 0 rows, writer `add-item` is a
**named refusal** in `db.py --help` output ("REFUSED — the item layer was deleted (owner,
2026-09-01)"), confirmed at the CLI dispatch. Every table with a `NOT NULL REFERENCES items(...)` FK
(`item_taxonomy_links`, `item_bpc_links`, `item_population_elaborations`, `item_audit_runs`,
`jurisdictional_values`, `room_items`, `term_item_links`, `case_study_specs`, `economics_entry_specs`,
`spec_value_probes`) is therefore **permanently** unwritable, not merely "empty for now" the way
`base_parameters`-dependent and `evidence_sources`-dependent tables are (those two parents have live
writers — `add-parameter`, `add-source` — so their downstream FK chains self-resolve the moment
someone calls them). This distinction (permanent vs. self-resolving "unwritable") is not visible
from the FK-emptiness snippet alone; it required checking whether the *parent's own writer* is live,
refused, or absent.
