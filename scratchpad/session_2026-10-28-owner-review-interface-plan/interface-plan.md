# Plan: an owner review-and-edit interface for the guidebook database

Session kind: **tooling** (RC6). Session anchor: `scratchpad/session_2026-10-28-owner-review-interface-plan`. Figures below were measured 2026-10-28; re-derive with the commands in "Derive, do not quote" at the end (CLAUDE.md rule 7a).

## Context

The owner said: *"I need there to be some kind of interface where I can manually review and edit the different table values/information and have it propagate accordingly. At the moment, everything in the database is opaque to me."*

State that makes this necessary: 56 tables and 22 views in a binary SQLite blob with no `sqlite3` CLI; no viewer, server or editor exists anywhere in `scripts/` (the old `tools/` was deleted by workplan step 1.1); the only planned reader, T-5's `render_cells.py`, is scoped to determinations, writes to `$TMPDIR`, and sits behind T-2 to T-4 and six owner rulings. The 2026-10-23 resolution workplan (and its correction, merged as PR #203 on 2026-10-27) contains no item for this; its closest text is H-0's one-line "owner queue" in `.claude/commands/orient.md` and the question register's E12 / D5 ("who reviews vocabulary in bulk", unanswered). Nothing in the pipeline reaches a reader yet: the 8 `specifications` rows are all retired.

Intended outcome, in the owner's terms:
1. Every table, row, pointer and vocabulary is visible and navigable.
2. The owner can see what is waiting on them, in one place.
3. The owner can propose a change to any value, with a warrant, and see what it would touch.
4. A change reaches the database only by the sanctioned path, previewed first, in its own PR.

## Constraints that fix the shape (not open to design)

- **Rule 3, no direct writes.** The database changes only by scratch copy, `db.py` verb, `emit_batch_sql.py`, `emit_data_migration.py`, `migrate_db.py`. So the page cannot write. An "edit" is a **proposal** that I apply through the verbs. Previewing is free: all 72 verbs take `--dry-run`, which rolls back.
- **Retire in place** (ruling 2026-09-16): an edit to a judged value is retire-and-replace or an amend verb, never a delete.
- **Rule 5 and 8, derive, do not copy.** The page derives tables, columns, keys, pointers and vocabularies from the database it embeds. It stores no second copy of any fact; the proposals queue is a work list consumed on apply.
- **Rule 10.** Tooling ships in a tooling-only PR merged first; the owner's data edits ship in a separate data PR.
- **Rule 9.** No PR watching; open each PR last; `unsubscribe_pr_activity` immediately after creating it.
- **Net-negative** (owner 2026-10-12, restated 2026-10-23): a PR touching `scripts/` does not raise the line total unless its description names the exception. This work adds code; see Owner decision 1.
- **Rule 0.** The owner's request above is a live statement and is recorded in the ledger before anything is built (Phase 0).

## Design (recommended approach)

**The page.** One self-contained HTML document, published as a private Artifact (a cloud session offers the owner no reachable server). It embeds the database file (5.1 MB, about 6.8 MB base64, under the 16 MB cap) and opens it in the browser with sql.js 1.10.3 from cdnjs (200 on the allowed CDN, pinned, older than two weeks). Everything shown is a query against that embedded copy: `sqlite_master`, `PRAGMA table_info`, `PRAGMA foreign_key_list`. A new table therefore appears with no code edit. The page stamps the database `sha256` and `PRAGMA user_version`, and says it is a snapshot.

Three things the browser cannot derive reliably are injected by a small build step, each from the existing single home of the fact:
- stage per table: `governance/stage-map.yaml` (`tables:`; `judged_by` and `judged_on` shown on the page);
- vocabularies: `dbcore.check_values()` for the 115 closed `IN` lists, `dbcore.check_expression()` printed raw for the 81 shape CHECKs (`LIKE`, `BETWEEN`, `json_valid`, cross-column state rules);
- the guard sets: `dbcore.ENGINE_SOURCE_COLUMNS`, `dbcore.ENGINE_EXTRACTION_COLUMNS`, and which `(table, column)` pairs have an amend verb (`_AMENDABLE` in `db.py`), so the page can say "sanctioned verb", "refused under a live determination", or "no verb: coverage gap".

**Screens.**
1. **Waiting on you.** A short list of named queries, each shown with its rows, plus the workplan's ruling sheet (OR-1 to OR-25, OW-1, OW-2) with defaults and the consequence of "no" from `workplan/2026-10-23-pipeline-resolution-workplan.md` §4 and the PR #203 copy. Answers are stored as rulings-to-record, not as database rows. **Membership is a judgment, not a derivation**: a vocabulary value naming the owner matches `adversarial_findings.verdict = 'WITHHELD-FOR-OWNER'` (awaiting), `adversarial_findings.disposition = 'OWNER-RULED'` (already decided) and `search_executions.origin = 'owner-supplied'` (not a wait), so the pattern alone mixes waiting with done. The queries therefore live in a small file stamped `judged_by` / `judged_on`, as `governance/stage-map.yaml` is, and the owner confirms the list when Phase 2 is accepted. Starting candidates: the withheld findings, `adversarial_findings.disposition = 'PROVISIONAL-DISPUTED'` (the dispute rule sends a doctrine-level dispute to the owner), `decisions` not ACTIVE, and open `determination_gates`.
2. **Stage index.** Tables grouped by stage with row count, empty flag, and the UNWRITABLE derivation from CLAUDE.md §4. The 30 tables whose DDL carries comments show them as hover text on columns.
3. **Table view.** Grid with sort, filter, search; vocabulary chips; foreign-key cells as links; retired rows dimmed; long text (up to about 14,000 characters in `gaps.description`) truncated with expand; JSON-in-TEXT columns pretty-printed; wide tables (`evidence_sources` has 97 columns) with column groups and a column picker; composite keys (14 tables) shown as the key tuple.
4. **Row view and "what depends on this".** Outbound pointers followed; inbound pointers counted per referencing table (derived from every `foreign_key_list`); views that read the table; determinations resting on the row (precomputed at build by `dbcore.determinations_resting_on`, so the junction logic is not written twice; empty today). Pointers with no foreign key are shown from a named list: `adversarial_findings.subject_table/subject_key`, `evidence_sources.superseded_by_ref_id`, `conflicts.gap_id`, `citation_mining.global_ref_id`.
5. **Edit (a proposal).** What the page offers per column is what the sanctioned verbs allow, derived from the injected sets, and nothing else:
   - **amend**, for columns a verb lets change (`_AMENDABLE` for `amend-source`; `_AMENDABLE_SVE_FIELDS` for `amend-extraction`, which per D-0168 admits only `figure_role`, `comparator`, `extraction_method`, `extraction_status`, `root_type`, `root_ref_id`);
   - **a second row (a contest)**, for a wrong value or claim text, which D-0168 forbids overwriting (`add-extraction`);
   - **retire or dispose**, never delete (LED-169, retire in place);
   - **read-only**, for `specifications` and the convergence and link tables the engine writes (the 2026-09-09 ruling: a determination is computed, not hand-assigned), and for any table with no verb ("no verb: coverage gap").

   A vocabulary dropdown, a foreign-key picker or text field, and a required warrant (the verbs refuse a blank reason anyway). An amend is applied to the in-browser copy only, so the 22 views recompute at once and the page shows which views changed and by how many rows; a contest inserts a row into the in-browser copy the same way. Columns in the guard sets are flagged "a determination would go stale: re-derivation needed". The change set lists `(table, key, action, column, old, new, warrant, database sha)`. There is no approve button: a page selection records what the owner chose, and the ledger entry that executes it quotes the owner's words (LED-154 delegates adjudication only for enumerated items, and OR-17 is unanswered).
6. **Send.** The change set is saved to the Artifact's `db` (collection `proposals`), and offered as a downloadable JSON as a fallback. Nothing else is persisted.

**The apply loop (me, not code).** On the owner saying "apply my proposals": read them with `ArtifactData`; reject any whose `old` differs from the live value or whose database sha is behind; for each, pick the verb (`amend-source`, `amend-extraction`, `amend-term`, `amend-gap`, `amend-search`, `amend-population-match`, `adjudicate-term`, `dispose-adversarial-finding`, `resolve-determination-gate`, `close-gap`, `retire-*`, others), run it `--dry-run` on a scratch copy, then for real on the scratch. Where a live determination is involved the chain is `retire-specification`, the amend, `assess_cell.py --db <scratch>`. Write each outcome back to the proposal (applied to scratch / refused with the verb's own reason / no verb) so the owner sees it in the page; on the owner's approval, `emit_batch_sql.py --scratch ...` then `emit_data_migration.py --session <stem>.md` then rehearse `migrate_db.py` on a copy. I write no wrapper script: the owner's edit volume is unknown (E12), and a mapping table from proposals to verbs would be a curated list that drifts (rule 8). Build one only if volume shows it is needed.

**Gaps are filed, not patched.** Eleven tables have no verb (`access_duration`, `access_needs`, `access_need_icf`, `access_stakes`, `base_taxonomy_identity`, `lang_jur_map`, `life_stage_modifiers`, `weighting_profile`, `slugs`, `rooms`, `decisions`). A proposal against one is reported "no verb" and recorded as a GAP; a verb is added in a tooling-only PR only when an owner edit actually needs it (rule 8: nothing is added without naming what reads it). `amend-term`, `amend-gap`, `amend-search`, `amend-population-match`, `adjudicate-term` check nothing against live determinations; the page cannot rely on them to refuse.

## Derive, do not quote

- tables / non-empty / views: `select count(*) from sqlite_master where type in ('table','view')` grouped by type, and a per-table `count(*)` loop.
- writable tables: `python3 -c "import sys;sys.path.insert(0,'scripts');import dbcore,sqlite3;print(len(dbcore.writable_tables(sqlite3.connect('file:data/guidebook.db?mode=ro',uri=True))))"`.
- live determinations: `select count(*) from specifications where retired_at is null`.
- no-verb tables: tables in `sqlite_master` not in `dbcore.writable_tables`, minus `data_migrations` and `sqlite_sequence`.
- closed vs shape CHECK columns: iterate `dbcore.check_values` and `dbcore.check_expression` over every column.
- owner-gated states: every CHECK value containing `OWNER` (`dbcore.check_values`), then count rows.
