## Task-file defects

Count: **11** (3 of them stop-class for a real execution's downstream tasks, 8 smaller).

1. **(worst) Replacing a carried link cannot be replayed from the captured batch.** Design section 6 "Captured set" says retirements are captured as UPDATEs and confirms only that the table is in `writable_tables`. I ran the real path on a scratch copy: `add-lens-link --identity MOB` on a figure with a carried MOB link, then `emit_batch_sql.py`. It wrote the new INSERT before the UPDATE that retires the carried link (it always orders inserts then updates within a table), and applying it fails: `sqlite3.IntegrityError: UNIQUE constraint failed: index 'ux_extraction_lens_live'`. With the UPDATE first, the replay reproduces the scratch table exactly. This is the main path T-106, T-102 and T-115 are told to use ("a judged link replaces a carried one in one call"), so every such research batch would produce an unappliable data migration. A corrected file needs: either an `emit_batch_sql` ordering rule for this table (updates before inserts, with a selftest) added to section 4, or a different replace design; and a capture round-trip case in section 10 (not only the writable-set check).
2. **(second worst) A blocking check that reads the changed table is missing from section 6's list and from the sweep.** `research_dod_selftest` (`research_batch_dod.py --selftest`, level blocking) builds a corpus by cloning the live schema and raw-INSERTs a figure naming `identity_code`; after the migration it dies with `IntegrityError: CHECK constraint failed: COALESCE(identity_code, ...) IS NULL`. The design section 9 names this file's fixture, but section 6's `CHECKS=` does not include the registered check, and the gate would be the only place to meet it. I added it to the before/after runs, and showed it crashes with the fixture unrepaired (stashed the fix, ran it). The list should be derived (every registry check whose cmd reads a script from the sweep's hit list), not typed.
3. **(third worst) The design leaves the Python-API shape undecided and depends on a task not in the stack.** Section 6 specifies the CLI flags, but every test that calls `db.insert_extraction` / `db.derive_extraction` with `identity_code` in a payload (about thirty call sites in three test files, via builders) now needs a basis and basis text, and the design says nothing on how the API receives them. I chose two non-column keys in the payload dict (`lens_basis`, `lens_basis_text`) and kwargs on `derive_extraction`; a corrected file should say so. Same cluster: "refuses a `deprecated` identity code (successor named) (T-054's general refusal, reused)": T-054 is neither a precondition in section 2 nor in this stack; no such refusal and no successor column exist (`base_taxonomy_identity` has only `status`).
