## 3. The problem, in the guidebook's terms

The pipeline holds quotations, terms, clauses and titles in many languages and has nowhere to put a translation of any of them. So text in different languages cannot be compared or discussed together, or a session translates in its head and the translation is lost, or, worse, an English paraphrase is written where the source's words should be and is later read as the source's. The owner asked that everything non-English be translated, "probably at synthesis or whatever we need".

## 4. The change

Order of preference, from CLAUDE.md §8: do nothing and say why; change a rule or convention; reuse what exists; delete the cause; only then add the smallest code that closes the defect.

1. **One table, `translations`, by schema migration.** A translation points at the cell it translates and never replaces or copies it. Columns: `translation_id` (`INTEGER PRIMARY KEY AUTOINCREMENT`, so any later table points at a translation by key); the pointer `source_table`, `source_column`, `source_row_key` (the value, as text, of the pointed table's **single-column declared primary key**, read from `PRAGMA table_info`; never a `rowid`, which a table without an integer key can renumber on a rebuild; a table whose primary key has more than one column cannot be pointed at and the verb refuses it, naming why: `term_aliases` is one today, see item 6); `source_sha256` (the hash of the cell's text when it was translated, so a later change to the original is seen; a hash is not a copy); `target_language`; `translated_text` (NULL only while requested); `status` with a CHECK (`requested`, `translated`, `reviewed`, `rejected`); `translator_kind` with a CHECK (`model`, `tool`, `person`) and `translator_name` (the model id, the tool and version, or the person), both required once `status` is past `requested`; `requested_at_stage` (the stage that asked); `due_stage` (NULL means the rule of item 4 decides; a value is an explicit override for this row); `reviewed_by_kind` (CHECK `model`, `tool`, `person`), `reviewed_by_name`, `reviewed_at`, required exactly when `status` is `reviewed` or `rejected`; `review_reason` (TEXT: why the reviewer decided; required when `status` is `rejected`, optional when `reviewed`, NULL otherwise); `superseded_by_translation_id` (`REFERENCES translations(translation_id)`, never the row's own id; a corrected translation is a new row; the old one is retired in place); and the four session and time columns every table carries (`created_at`, `created_by_session`, `updated_at`, `updated_by_session`, filled by `dbcore.stamp_for`). CHECKs hold those consistency rules: `translated_text` is NULL exactly when `status` is `requested`; translator kind and name are both NULL when `requested` and both set otherwise; the three reviewer columns are all set when `reviewed` or `rejected` and all NULL otherwise; `reviewed_by_name <> translator_name` (item 8); `status <> 'rejected' OR review_reason IS NOT NULL`; `status IN ('reviewed','rejected') OR review_reason IS NULL`. Chosen (pilot 2026-11-13): `review_reason`. Item 3 has `review-translation` take "a reason on rejection" and this list as first written had no cell for it, so the verb could not keep what it was told to require; the pilot added the column and stopped short of the section 8 stop. One column on the row, not a reviews table: item 1 already holds one review per row (a second review of the same text is a new translation row by `--supersedes`), and the reason is one fact in the cell that names it (the 2026-11-06 schema-shape statement); writing it into a note or into `translated_text` would join two facts in one cell. There is no column that says "this is a translation": the table is the mark, and a flag that is always true informs nobody.
2. **One view, `v_translations_current`:** rows that are `translated` or `reviewed` and not superseded. It is the only read surface. It never names `translated_text` as if it were a source column, and nothing joins it into a view under the name of the column it translates.

5. **Fidelity, checked at `record-translation`.** The original is kept by construction (it is never touched). The numbers must agree: with the number reader of T-008, every number the original cell states as a numeral must be stated in the translation, and every number the translation states must be stated in the original or, where the pointed cell is the `claim_text` of a figure, be a number of that row's verified `claimed_value` (this covers a number the source writes in words). A translation that adds, drops or changes a figure is refused. A translation of a cell whose hash no longer matches is refused: request it again. How the numbers are read, so that the rule refuses what it should and nothing else. Chosen (pilot 2026-11-13; the file as first written said none of it, and without the first step the probes failed for the wrong reason):
   - The reader is the one T-008 adds beside `normalise_quote` in `scripts/research/retrieval_log.py` (`git grep -n -A3 'def numbers_stated' scripts/research/retrieval_log.py`; if T-008 merged it under another name, find it beside `normalise_quote` and use it; never write a second reader).

   - Both are read on the quote side (`quote=True`): the operands of a symbol ratio and the pieces of a space-grouped number count as stated numbers.
   - Compare the sets of number readings, not ratio tokens and not counts: a number of one text is matched when one of its readings is a reading of some number of the other (an ambiguous `1.200` matches either 1.2 or 1200); a number stated twice need not be stated twice. Ratio tokens themselves are not compared as pairs, because languages order a ratio's terms differently (十二分の一 names 12 before 1); their operands, compared as numbers, carry the check.
