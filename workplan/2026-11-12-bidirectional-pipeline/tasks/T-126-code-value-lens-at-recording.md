## 3. The problem, in the guidebook's terms

The owner ruled that every code value has a lens even where the code does not state one, assigned by contextual judgment (OD-65), by the session that records the row, when it has the clause and its context in front of it ("at the moment of recording the row is when you will have best idea of context"). Codes rarely name the people a clause serves: a mounting height or a knee clearance is written for everyone and serves wheelchair users ("typically anything to do concerning mounting height will concern wheelchair users"). Populations are coded "as a result" of the ICF and access-need links ("ICF and access needs are supposed to be mapped to populations too so populations still get coded as a result"): the maps from those codes to groups tell the recording session which groups to consider, and the session judges and writes them. Today the writer has no way to record that judgment honestly. A lens link's warrant (`extraction_lens_links.basis`) admits only that the figure's own words name the group, that its heading does, or that a study's participants are the group (or `carried`, which only migration 131 writes), and `_require_lens_warrant` refuses any warrant whose words are not found in the place the basis names; and nothing shows the session which groups the maps tie to the codes it is writing. So a session recording a code value either files it under words that do not name the group (a false warrant), or under `ALL`, which OD-31 removes from the identity lens, or leaves the group out; every stored code value still carries only the warrant-less `carried` links migration 131 moved. The engine reaches a cell only through the links written on a figure (D-0184; OR-1), so a group left unwritten is a cell the code value never reaches.
