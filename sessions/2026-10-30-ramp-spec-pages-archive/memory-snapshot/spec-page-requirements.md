Owner requirements for the spec pages (stated 2026-10-29 while reviewing sample pages), implemented as a pilot on **E-03** (`site/specs/e-03.html`, generated by `scripts/generate/spec_page_v2.py` from `data/spec_pages/E-03.json` + the DB):

- **Jurisdiction comparison must be exhaustive**, as accordions: top line = jurisdiction + salient standard/clause/value/note; expansion = everything else. Every jurisdiction in the search roster is listed, including "no entry yet".
- **Values are never a bare range under "ALL".** Three tiers (matches `design_scale` in migration 024): *for everyone* (ALL = universal, not a population), *for a specific group / ICF code / access need*, *for one person*. Each value must say who it is for.
- **Filter by population, ICF code, access need** (driven by migration 026 tables `icf_codes`, `access_needs`, `population_icf_map`, `source_*_tags`).
- **Unit selector** per page: metric/imperial/as-stated length; slope as ratio/percent/degrees/as-stated. Values are stored as structured numbers (tokens `{{slope=..|..}}`, `{{len=mm|..}}`), never baked into text.
- **No jargon** for users: "Mode P/S/Universal Mode" replaced by plain tier labels.
- **"Why it matters" = bullets with line breaks**, each tagged by where its evidence lives (in library / outside library / regulatory).
- A page's title must be the item name (never the BPC slug); A-01's page was wrong because its header/value came from a different record (threshold-door-hardware) than its text.

**Why:** the owner wants pages usable by policy and design audiences who cannot decode internal codes, and every figure traceable to who it serves and how it was verified.

**How to apply:** new/regenerated spec pages should follow `spec_page_v2.py`; only the E-03 pilot exists. The 72 other `site/specs` pages carry an "under review" banner and still show the old, wrong layout. ICF/need vocabularies and all source tags are PROVISIONAL/UNREVIEWED (see [[project-end-goal]], [[contract-traceability-invariant]]); only US ADA text was verified from a primary source for E-03.

**Jurisdiction scope (owner, 2026-10-29):** "buckets 1 and 2" = the leading jurisdictions (e.g. Canada, USA, Australia, Japan, Norway, etc.) plus a second group (e.g. Italy, China, etc.). The exact lists are not recorded anywhere in the repo or DB; ask the owner to confirm before treating any list as definitive. Order of work: (1) extract everything possible from the current codes/standards of all jurisdictions; (2) then look for higher-tier evidence (T1-T3, any language, any jurisdiction) for approaches that go beyond the codes. See [[current-state-only]], [[code-baselines-accepted]], [[methodology-lives-in-synthesis]].
**Where the jurisdiction definition lives (found 2026-10-29):** `workplan/workplan-jurisdiction-sweep.md` (priority groups P1 Core US UK AU CA DE NO SE ISO EU; P2 Extended European FR CH NL DK FI BE IE ES IT PT; P3 Asia-Pacific JP SG NZ KR CN; P4/P5 Global South) and `governance/jurisdiction-philosophy.md` (24 canonical jurisdictions + ISO/EU meta-codes, selection criteria). The owner's "bucket 1/2" examples (CA US AU JP NO, then IT CN) cut across the P-groups, so the exact cut is still unconfirmed.
**Master comparison table (owner, 2026-10-29):** for ramp gradient (and by extension any item with a numeric value) the page also needs an easy comparison master table: one row per jurisdiction showing the value it has (preferred, absolute maximum and its condition, run/rise between landings, verification level), unit-selector aware, above the detailed accordions.
**No "Not set" rows (owner, 2026-10-29):** a population/group value card whose status is "no evidence / Not set" must not be shown on the page at all. Absence of a card is the signal; only render values that have content. (Applies to value cards; the staged data may keep the placeholder.)
**Citations (owner, 2026-10-29):** every "In the library" reference is shown as an APA in-text citation (author or body + year), clickable; the popup shows the full APA bibliographic citation and, under the entry, lists all pages where that source has been cited. Do not show raw REF-ids as the visible label.
**No "outside the library" evidence (owner, 2026-10-29):** evidence is binary: either we have it (recorded in the library) or we do not. The library is simply what has been recorded. Anything found and relied on must be ingested and cited like any other source; never label evidence as "outside the library" or "external" on a page.
**Countries shown (owner, 2026-10-29):** show only the major identified countries for now (the P1+P2+P3 set from workplan/workplan-jurisdiction-sweep.md: US UK AU CA DE NO SE ISO EU; FR CH NL DK FI BE IE ES IT PT; JP SG NZ KR CN). Do not list the rest of the 47-code roster (e.g. Brazil) on the page; keep their data staged.
**Design (owner review, 2026-10-29, supersedes any earlier note):** do NOT use the site's `assets/guidebook.css` look (cream/yellow palette, Roboto Slab, JetBrains Mono): owner dislikes it. Take only the *information organisation* from the book era (plain jurisdiction tables with a Guidebook row, terse value-first bullets, one evidence line). Style rules: neutral white/grey with one blue accent (never yellow/cream), ONE system sans typeface, five type sizes only (32/24/18/16/14), 3 weights, no uppercase tracked labels, no pills/chips tropes, no tinted section colours; section identity = numbered heading with heavy top rule + sticky nav that tracks the current section; fewest controls (units as two dropdowns, filters as a collapsed row of three lens buttons, pills appear beneath only on click); evidence is alphabetical by last name and regroups by the active lens; in comparison tables the standard name is a small italic full-width line under each row; keep text short and values prominent. Generator: `scripts/generate/spec_page_v3.py` (writes `site/specs/<item>.html`; ALL spec pages live in site/specs, consolidated 2026-10-30); v2 is superseded. Test over a local http server (the browser pane's file view cannot load relative CSS).
**ACCESSIBILITY IS A HARD CONSTRAINT (owner, 2026-10-29):** all site work must comply with web accessibility standards and best practices: WCAG 2.2 AA minimum plus COGA (project standard in governance/armature_v3_review.md). Wins any conflict with aesthetics. Itemised, testable list in audits/spec-page-design-requirements-2026-10-29.md section 6a; never self-certify compliance, record what was actually tested.
**Design analysis (2026-10-29):** the consolidated reconciliation of all owner design feedback is audits/spec-page-design-requirements-2026-10-29.md. It supersedes the scattered design notes above; redesign waits for the owner's answers to its section 8.
**DEFINITION OF BEST PRACTICE (owner, 2026-10-29, stated repeatedly; supersedes any "Guidebook position/working position"):** the Guidebook takes no positions. Best practice = the best way to do something according to how it benefits the intended group; it is NOT the most common or most agreed value. It is the most accommodating/gentlest value found in any current standard (including preferred values) unless an academic article or professional body improves on it. Never present "most common" or "agreed" values as best practice; never label something a Guidebook position or recommendation. Judge per item and per population: the question is always who benefits and how much. Legal maximums are floors for comparison, shown as such.
**Doctrines to honour on every spec page (read 2026-10-29):** governance/mission-and-epistemics.md (CANONICAL: thinking tool, questions-led, not a prescription manual, within-population variability, best practice by evidence hierarchy not code consensus, Co-1 co-primary), references/project-standards.md Core Doctrine (advocacy project not an authority: no "shall be"; every specification carries evidence marker ● evidence-based or ○ inferred; person tier = OT assessment), governance/audience-priority.md (designers and disabled people primary; OTs and policymakers secondary), governance/tier-system.md. Open owner decisions recorded in audits/spec-page-design-requirements-2026-10-29.md section 10. Controls (units, three lenses, filters) must sit ABOVE all information. Do not highlight the steepest slope allowed in the codes.
**Pills (owner, 2026-10-29, relaxes the earlier "too many pills"):** pills are allowed if used judiciously (filter options, applied filters, similar controls). Only decorative or status pills are the trope to avoid.
**Minimalism must not cost legibility (owner, 2026-10-30):** especially for accessibility of website navigation. Navigation at least body size (16px+), dark, current location visible at load, visible control state; no small grey glyph cues. See audits/spec-page-design-defects-2026-10-30.md and requirements R16.

**Owner clarifications, 2026-10-30 (answers to my open confusions):**
- Two lenses: an AUDIENCE lens (designer, disabled person, OT, policymaker; changes which sections open by default, as in the e-08 exemplar) and a DISABILITY lens (population, ICF code, access need; the filters built so far). Only the disability lens exists on the v3 page; the audience lens is still to build.
- Buckets 1+2 are P1+P2+P3 (confirmed).
- "Covered" means the listed source has been read, had information extracted, and been VERIFIED. The page's "read" count is therefore not "covered"; currently 0 verified.
- Pages must ideally render directly from the database, not hand-staged JSON.
- "Specification" in the book and the item pages are the same idea: the correct way to design something.
- Best practice: the gentlest/most accommodating value found in practice IS best practice; no academic study is required (they are often unavailable). Existence in practice is the evidence. (This differs from the mission doc's "T4-T6 walled off from best-practice anchoring"; the owner's statement needs a doctrine decision record.)
- "Provisional" = the source must be re-read and the information confirmed; it is a review stage, not weak evidence. Provisional is a stage, not a permanent state.
- Tier numbering: governance/tier-system.md (OPERATIVE 2026-05-25) is the most recent and governs; project-standards line 17 and older notes are stale.
- Owner hypothesis on E-03: the problem is the lack of a rest landing, not the slope itself. The book spec pairs 1:20 with a rest platform every 9 m (>=1500x1500 mm); codes differ widely on landing spacing.
